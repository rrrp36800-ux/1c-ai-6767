# Архитектура development loop

## Цель

Этот документ описывает каркас для будущей разработки решений 1С:Предприятие 8.3 через AI-агентов. На этой ветке прикладных объектов 1С нет: `src/` и `tests/` подготовлены как точки расширения.

## Основной цикл

```text
AI agent
  → изменение исходников
  → статический анализ BSL
  → сборка
  → unit tests
  → UI/integration tests
  → краткий machine-readable report
```

### 1. AI agent

Агент читает `AGENTS.md`, задачу и текущий `reports/test-summary.json`, затем предлагает минимальное изменение. Агент не должен считать задачу завершённой по одному только виду файлов.

### 2. Изменение исходников

Будущие исходники конфигураций, расширений, внешних обработок и связанных XML/BSL-артефактов размещаются в `src/`. Сгенерированные бинарные результаты и локальные файлы окружения не являются исходниками и должны быть отделены от этого каталога.

### 3. Статический анализ BSL

После изменения `.bsl`/`.os` должен запускаться подтверждённый экземпляр BSL Language Server. Результат должен сохраняться в машиночитаемом виде. Конкретная команда и версия намеренно не зафиксированы до проверки на целевой машине.

### 4. Сборка

Сборка отделена от анализа: она должна проверять, что исходники можно импортировать/собрать средствами 1С. Операции, требующие конфигуратора или runtime 1С, выполняются только на машине, где 1С:Предприятие 8.3 действительно установлена.

### 5. Unit tests

Бизнес-правила и изолированные модули должны проверяться без UI, когда это возможно. Планируемый кандидат для 1С-тестов — YaXUnit; его конкретная интеграция с этим репозиторием ещё не подтверждена.

### 6. UI/integration tests

Сюда относятся проверки управляемых форм, обмена с информационной базой и пользовательских сценариев. Они требуют согласованного тестового стенда 1С и тестовых данных; на текущей ветке такие проверки не запускаются.

### 7. Краткий отчёт

`reports/test-summary.json` — первый файл, который должен читать AI. Полные логи и подробные отчёты должны открываться только при необходимости. Рекомендуемый минимальный набор полей:

```json
{
  "schemaVersion": 1,
  "status": "not_run | blocked | passed | failed",
  "generatedAt": "ISO-8601 timestamp",
  "checks": [
    {
      "name": "check-name",
      "status": "not_run | blocked | passed | failed",
      "details": "short explanation",
      "log": "optional/path/to/log"
    }
  ],
  "nextAction": "short actionable hint"
}
```

Статусы `passed` и `failed` допустимы только после реального запуска соответствующей проверки. Отсутствие 1С или ненастроенной команды означает `not_run`/`blocked`, а не успешный результат.

## Границы ответственности

- **AI:** анализирует задачу, меняет файлы, запускает доступные проверки, читает summary и объясняет ограничения.
- **Git/GitHub:** хранит историю, изолирует работу по веткам и принимает изменения через Pull Request.
- **Локальная 1С:** предоставляет конфигуратор/runtime для операций, которые нельзя достоверно выполнить только по XML/BSL-файлам.
- **CI:** в будущем повторяет детерминированные проверки на подготовленном runner, но не заменяет доступ к совместимой 1С.

## Что намеренно не сделано

- нет бизнес-логики;
- нет обработок, справочников и документов;
- нет фальшивых тестов и PASS-результатов;
- нет GitHub Actions workflow с непроверенными командами;
- нет фиктивной интеграции с 1С.

Следующий этап должен сначала подтвердить toolchain на реальной Windows-машине, а затем добавить одну минимальную вертикальную проверку от исходника до summary.
