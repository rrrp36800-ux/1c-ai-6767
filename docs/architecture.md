# Архитектура development loop

## Цель

Этот документ описывает каркас для будущей разработки решений 1С:Предприятие 8.3 через AI-агентов. В текущем PR прикладных объектов 1С нет: `src/` остаётся точкой расширения, а в `tests/` находится только минимальный fixture для статического анализа.

## Основной цикл

```text
AI agent
  → изменение исходников
  → статический анализ BSL
  → сборка
  → unit tests
  → UI/integration tests
  → краткий machine-readable report
```

### 1. AI agent

Агент читает `AGENTS.md`, задачу и текущий `reports/test-summary.json`, затем предлагает минимальное изменение. Агент не должен считать задачу завершённой по одному только виду файлов.

### 2. Изменение исходников

Будущие исходники конфигураций, расширений, внешних обработок и связанных XML/BSL-артефактов размещаются в `src/`. Сгенерированные бинарные результаты и локальные файлы окружения отделяются от этого каталога.

### 3. Статический анализ BSL

Первый исполняемый слой реализован в `scripts/test-bsl.ps1`. Он:

- проверяет Java 17 или новее;
- скачивает официальный `bsl-language-server-1.0.7-exec.jar`, если его нет локально;
- проверяет SHA-256 JAR;
- запускает подтверждённую команду `java -jar ... --analyze --srcDir ... --reporter json --outputDir ...`;
- сохраняет JSON-отчёт и полный лог отдельно;
- считает анализ успешным только при нулевом количестве диагностик severity `Error`.

Локальная 1С для этого шага не требуется. Предупреждения учитываются в отчёте, но сами по себе не делают проверку неуспешной.

### 4. Сборка

Сборка отделена от анализа и должна проверять, что исходники можно импортировать или собрать средствами 1С. Операции, требующие конфигуратора или runtime 1С, выполняются только на машине с установленной 1С:Предприятие 8.3.

### 5. Unit tests

Бизнес-правила и изолированные модули должны проверяться без UI, когда это возможно. Планируемый кандидат для 1С-тестов — YaXUnit; его интеграция с этим репозиторием ещё не подтверждена.

### 6. UI/integration tests

Сюда относятся проверки управляемых форм, обмена с информационной базой и пользовательских сценариев. Они требуют согласованного тестового стенда 1С и тестовых данных; на текущей ветке такие проверки не запускаются.

### 7. Краткий отчёт

`reports/test-summary.json` — первый файл, который должен читать AI. Полные логи и подробные отчёты открываются только при необходимости.

Схема summary:

```json
{
  "schemaVersion": 1,
  "scope": "bsl-static-analysis | full-pipeline | bootstrap",
  "status": "not_run | blocked | passed | failed",
  "generatedAt": "ISO-8601 timestamp",
  "generatedBy": "producer name",
  "reason": "optional short explanation",
  "checks": [
    {
      "name": "check-name",
      "status": "not_run | blocked | passed | failed",
      "details": "short explanation",
      "report": "optional/path/to/report",
      "log": "optional/path/to/log"
    }
  ],
  "logFiles": [],
  "nextAction": "short actionable hint"
}
```

Новые producers должны заполнять поля по смыслу. Статусы `passed` и `failed` допустимы только после реального запуска соответствующей проверки. Отсутствие зависимости или ненастроенной команды означает `blocked`, а ещё не запускавшаяся проверка — `not_run`.

### Exit codes для CI

`./scripts/test-bsl.ps1` и `./scripts/test.ps1` используют fail-closed контракт:

- `0` — все проверки выбранного scope завершились успешно (`status: passed`);
- `1` — обнаружена ошибка структуры, запуска или анализа (`status: failed`);
- `2` — проверка заблокирована окружением или ещё не настроена (`status: blocked`).

`./scripts/test.ps1 -BslOnly` запускает только доступный BSL-слой и используется GitHub Actions. Обычный `./scripts/test.ps1` также включает будущие 1С build, unit и UI/integration checks; пока они не настроены, его общий результат остаётся `blocked`, даже если BSL-анализ прошёл.

## Границы ответственности

- **AI:** анализирует задачу, меняет файлы, запускает доступные проверки, читает summary и объясняет ограничения.
- **Git/GitHub:** хранит историю, изолирует работу по веткам и принимает изменения через Pull Request.
- **Локальная 1С:** предоставляет конфигуратор/runtime для операций, которые нельзя достоверно выполнить только по XML/BSL-файлам.
- **CI:** текущий workflow запускает BSL-слой без 1С; остальные проверки будут добавлены только после подтверждения их toolchain.

## Что намеренно не сделано

- нет бизнес-логики;
- нет обработок, справочников и документов;
- нет сборки `.epf`;
- нет YaXUnit и UI/integration tests;
- нет фальшивых PASS-результатов;
- нет фиктивной интеграции с 1С.

Следующий этап — подтвердить toolchain для сборки и тестирования на реальной Windows-машине, а затем добавить соответствующие проверки в full pipeline.
